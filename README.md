Логика решения:
1. Преподаватель заводит список студентов группы и формирует рубрикатор курса(перечень критериев оценивания), для каждого из которых задаются название, максимальный балл и вклад в итоговую оценку
2. Преподаватель выставляет студентам баллы по критериям, а также может исправить или отменить ранее поставленную оценку
3. Итоговый балл при каждом запросе сводки заново вычисляется на основе актуальных оценок студента и весов критериев по выбранному правилу расчета с применением округления
4. Все изменения автоматически сохраняются в локальное хранилище (`pos_data.json`), а итоговую ведомость по группе можно вывести в консоль или экспортировать в форматы CSV и JSON

Управление:
- students, add student, del student - просмотр, регистрация и удаление студентов.
- rubric, add criterion, edit criterion, del criterion - управление рубрикатором курса.
- grade, cancel grade - выставление, изменение и отмена оценок по критериям.
- summary - просмотр выставленных оценок и расчет итогового балла (доступны стратегии normalized и sum).
- export - выгрузка итоговой ведомости в csv или json.
- demo - прогон сквозного демонстрационного сценария.

Карта DDD:
1. Ubiquitous Language:
   - Студент (Student) - обучающийся на курсе, которому выставляются оценки.
   - Критерий (Criterion) - элемент оценивания с названием (Title), максимальным баллом (MaxScore) и вкладом в итог (Weight).
   - Рубрикатор (Rubric) - набор критериев конкретного курса, определяющий правила оценивания.
   - Оценка (Evaluation) - факт выставления студенту балла (Score) по конкретному критерию с отметкой времени (EvaluatedAt) и необязательным комментарием (Comment).
   - Зачетная ведомость (StudentGradebook) - журнал оценок конкретного студента по критериям курса.
   - Итог (FinalGrade) - итоговый балл студента, вычисляемый по его оценкам и весам рубрикатора (не хранится как произвольное число).
2. Entity и Value Object:
   - Entities (Student, Rubric, StudentGradebook) - Идентифицируются по уникальному ID. Например, при изменении ФИО или группы (Student.UpdateInfo) студент остается той же сущностью с тем же StudentId.
   - Value Objects (StudentId, CriterionId, MaxScore, Weight, Score, Evaluation, FinalGrade) - Не имеют собственной идентичности, сравниваются по значению полей, иммутабельны после создания и валидируют свои инварианты в конструкторе. Например, Score гарантирует попадание балла в границы, а MaxScore и Weight — строго положительные значения.
3. Инварианты:
   - Student хранит профиль студента (Id, FullName, Group), запрещает пустые ФИО и название группы.
   - Rubric  владеет коллекцией сущностей Criterion. Охраняет уникальность названий критериев в рамках курса и не допускает пустых/некорректных параметров критерия.
   - StudentGradebook охраняет ключевые инварианты: нельзя выставить оценку по критерию, которого нет в Rubric, нельзя записать балл, превышающий MaxScore критерия.
4. Repository (порт):
   - Интерфейсы IStudentRepository, IRubricRepository и IGradebookRepository объявлены в слое Domain/Repositories
   - Детали хранения в JSON-файле (JsonStorage), DTO и маппинг (Riok.Mapperly) полностью изолированы в Infrastructure.
5. Domain Service:
   -FinalGradeCalculationService: расчет итогового балла требует одновременного участия двух агрегатов (StudentGradebook и Rubric), а также выбранной стратегии расчета, поэтому не принадлежит ни одной сущности единолично и вынесен в доменный сервис.

Архитектура и слои:
Выбрана облегченная слоеная архитектура Ports & Adapters (Hexagonal / Clean Architecture)-
PosApp/
├── Domain/             # Ядро: Entities, Value Objects, Aggregates, Domain Service, Factory, Builder, Strategy, Ports
├── Application/        # Прикладные сервисы (Use Cases) и абстрактный шаблон экспорта (Template Method)
├── Infrastructure/     # Адаптеры хранения (JsonStorage, DTO, Mapperly-мапперы, Repositories) и экспортеры CSV/JSON
├── Presentation/       # Фасад сценариев (PosConsoleFacade) и консольный UI (ConsoleUi)
└── Program.cs          # Composition Root: сборка графа зависимостей через Microsoft.Extensions.DependencyInjection

- Domain не имеет ни одной зависимости
- Application зависит от Domain
- Infrastructure и Presentation зависят от Application и Domain
- Program.cs выступает единым Composition Root, связывая интерфейсы и реализации


Обоснование GoF:
1. Порождающие:
   - Factory(EvaluationFactory (Domain/Creation/)) - Единая точка создания Evaluation: проверяет существование критерия в Rubric, валидирует попадание балла в границы и фиксирует время.
   - Builder(RubricBuilder (Domain/Creation/)) - Упрощает пошаговую декларативную сборку рубрикатора курса и гарантирует на этапе Build(), что рубрикатор не пуст и все веса валидны.
2. Структурные:
   - Decorator - Добавляет правило округления итогового балла.
   - Facade - Предоставляет консольному интерфейсу единую точку входа ко всем сценариям.
3. Поведенческие:
   - Strategy - Позволяет переключать формулу расчета итогового балла.
   - Template Method - Фиксирует общий алгоритм выгрузки итоговой ведомости.
